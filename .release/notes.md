# Quality Gate 2.1.0

Добавлен общий механизм подготовки и публикации релизов для репозиториев-потребителей. Он проверяет релизное решение в PR, сохраняет исходный кандидат после слияния и публикует релиз после проверки происхождения и содержимого артефактов.

Повторный запуск проверяет уже завершённый релиз или дозагружает недостающие файлы совпадающего draft. Восстановление по номеру слитого PR сохраняет первоначальные исходники и разрешение публикации при обновлении инструментария. Общий интерфейс поддерживает доказательства для архивов, образов и пакетов.

Исправлено получение журналов GitHub Actions при публикации через GitHub CLI 2.100 и новее. При отказе CLI из-за управляющих последовательностей запрос журнала повторяется один раз с явным разрешением; HTTP-ошибки, тайм-ауты и другие отказы по-прежнему останавливают публикацию.

CLI, schema 2, контракт hook/runtime v2 и Windows/Linux ZIP сохраняют совместимость. Существующим потребителям адаптация не требуется. Подключение общего publisher и переход на новую версию Quality Gate выполняются явно: reusable workflows и helper выбираются по одной полной ревизии, принятой после публикации и проверки релиза. Автоматического обновления потребителей или развёртывания сервисов нет.

# Quality Gate 2.2.0

Изменение MINOR относительно v2.1.0: общий publisher получает доступ к GHCR через короткоживущий `GITHUB_TOKEN` вызывающего workflow. `RELEASE_TOKEN` используется только для GitHub Release API, а producer-job получает собственный `GITHUB_TOKEN` с `packages: write`. Для приватного GHCR-пакета в другом репозитории владелец пакета один раз выдаёт вызывающему репозиторию Read в **Manage Actions access**.

Проверка provenance связывает artifact с job из той же producer-попытки. Успешный повторно использованный job может подтвердить artifact предыдущей попытки только при совпадении API-записей обеих попыток. Publisher ограниченно повторяет запросы при неполных данных GitHub API и останавливает публикацию с диагностикой, если evidence отсутствует или не совпадает.

Quality Gate, parity и release-процессы используют отдельный временный каталог в корневом `temp/` проверяемого репозитория. При запуске удаляются оставшиеся неактивные каталоги, а временные каталоги кэша и атомарной замены остаются рядом со своими постоянными целями. Для read-only checkout и candidate snapshot используется закрытый хешированный per-repository workspace в пользовательском системном temp. Каждый consumer должен добавить `/temp/` в свой `.gitignore`.

Consumers обновляют Quality Gate и reusable-workflow revision только отдельным явным изменением после проверки опубликованного релиза. ARGUS_TG и ARGUS_tracker в этой версии не переключаются.

# Quality Gate 2.3.0

Изменение MINOR относительно v2.2.0: общий publisher публикует образы в GHCR через отдельный проверяемый writer. Writer сверяет исходную ревизию образа с одобренным исходным кодом, а publisher до изменения GitHub Release проверяет сохранённое подтверждение публикации и читает образ обратно по его неизменяемому digest. Для GHCR и GitHub Release используется автоматически выданный `GITHUB_TOKEN`; отдельный `RELEASE_TOKEN` или GHCR PAT не нужен. Job publisher получает только `contents: write`, а отдельный вызов writer — только `packages: write`. Для приватного пакета в другом репозитории владелец один раз настраивает доступ вызывающего репозитория в **Manage Actions access**.

# Quality Gate 2.4.0

Добавлено узкое исключение политики для автоматического запроса ревью владельца на Dependabot PR. Quality Gate разрешает job-scoped `pull-requests: write` только для точного утверждённого шаблона `.github/workflows/dependabot-review.yml`: `pull_request_target` для недрафтовых PR бота в `main`, выбор владельца репозитория, защита от повторного запроса и ограниченное время выполнения. Изменение пути, триггера, guards, прав, окружения, команд или шагов закрывает исключение. Checkout PR и выполнение кода продукта в этом шаблоне не разрешаются.

Это новая обратно совместимая возможность, MINOR относительно v2.3.0. CLI, schema 2, hook/runtime v2 и Windows/Linux ZIP сохраняют совместимость. Существующим потребителям адаптация не требуется. Для подключения reviewer workflow нужно явно обновить опубликованную policy/helper-пару; сам workflow включается отдельным изменением после проверки релиза. Публикация не обновляет потребителей автоматически и не развёртывает сервисы.

# Quality Gate 2.4.1

Исправлено определение отсутствующего точного GHCR version-tag на этапе общей публикации. Writer продолжает работу только при явном полном ответе об отсутствующем manifest именно этого тега и без сохранённого receipt digest; прочие ошибки доступа к Docker/GHCR остаются отказами.

# Quality Gate 2.4.2

Уточнена предварительная проверка GHCR: writer распознаёт подтверждённое отсутствие точного version-tag, включая ответ Docker `not found`, только для ожидаемого тега без сохранённого receipt digest. Сообщения о сбоях Docker теперь называют разрешённую подкоманду без вывода ссылок на образы, аргументов, путей или секретов. Ошибки других тегов, доступа и сети по-прежнему останавливают публикацию.

# Quality Gate 2.5.0

Shared release validation автоматически принимает отсутствующий раздел `## Release` как `No release` только для PR от `dependabot[bot]`, если полный список затронутых путей состоит из YAML-файлов непосредственно в `.github/workflows/`. Проверка читает текущие и прежние имена файлов через GitHub API; смешанные изменения, переименование из кода и нестабильный или неполный список по-прежнему требуют явного решения. В PR-теле ничего не меняется.

Это новая обратно совместимая возможность, MINOR относительно v2.4.2. CLI, schema 2, hook/runtime v2 и Windows/Linux ZIP сохраняют совместимость. Provider и потребители должны отдельно синхронизировать опубликованную policy/helper-пару и совместимый полный SHA reusable workflows, чтобы получить правило в CI. Публикация не обновляет потребителей автоматически и не развёртывает сервисы.

# Quality Gate 2.6.0

Добавлены `quality-gate edit-check` и короткий entry point `quality-gate-edit`: ограниченная JSON-проверка явно заданных рабочих Python-файлов с безопасной сортировкой импортов, форматированием и проверкой итогового содержимого. Неиспользуемые импорты `F401` сохраняются; форматирование выполняется и при оставшихся lint-ошибках. Результат содержит финальные координаты и SHA-256 без фрагментов исходников, текста исключений или значений секретов.

Managed-файлы используют точный закреплённый policy release и подготовленный runtime своего компонента. Файлы вне компонентов и вне Git используют явно выбранный baseline и заранее установленный Python. Новый engine поддерживает прежние pins `v2.4.2` и `v2.5.0`, не изменяя их; для остальных pins требуется явная проверка совместимости и обновление по установленной процедуре. Перед использованием нужно отдельно выполнить `edit-setup` для каждого выбранного релиза; редактирование работает offline, без установки зависимостей и запуска полной проверки.

Это обратно совместимая возможность, MINOR относительно v2.5.0. Обычные проверки, schema 2, Git hooks и политика Ruff сохраняются. Релиз не устанавливает Codex hooks, не активирует baseline и не обновляет потребителей автоматически. Подключение требует опубликованного engine и отдельной проверки регистрации, результата и задержки на стороне host; контракт описан в `docs/edit-check.md`.

# Quality Gate 2.6.1

Исправлен запуск `edit-check` штатным native release launcher прямо из проверенного wheel на `PYTHONPATH`. В v2.6.0 путь к архиву ошибочно использовался как рабочий каталог дочернего процесса, что давало `unchecked/io` до проверки файлов. Worker теперь запускается в собственном временном workspace, сохраняя явный импорт выбранного engine и изолированный Python.

Это PATCH относительно v2.6.0. Schema 1, короткие ответы об ошибках, правила Ruff и exact-policy pins v2.4.2/v2.5.0/v2.6.0 сохраняются. После публикации требуется явно установить исправленный engine v2.6.1; опубликованные assets и кэши v2.6.0 не заменяются. Активация host и приёмка задержки по прежним целям выполняются отдельно.

# Quality Gate 2.6.2

Устранены повторные запуски Ruff для неизменившегося полного набора файлов. Engine заново проверяет точный policy release, инструмент, Python/runtime, конфигурацию, waiver и dependency inputs; повторное использование допускается только при полном совпадении идентичностей и влияющей на сортировку импортов структуры локальных модулей. Сохраняются и успешные результаты, и найденные ошибки с финальными координатами и SHA-256. Повреждение или недоступность ограниченного локального кеша возвращает обычную проверку Ruff.

Это PATCH-оптимизация относительно опубликованной v2.6.1. Schema 1 и правила Ruff сохраняются; host продолжает отправлять обычный запрос со свежими SHA и дедлайном. На повторном результате `input_sha256` соответствует текущему запросу, `changed=false`. Для использования нужен явно установленный опубликованный engine v2.6.2; существующий policy pin, включая v2.4.2, менять не требуется. Релиз не изменяет Codex hooks, настройки, регистрацию или доставку сообщений host.

# Quality Gate 3.0.0

Добавлена `quality-gate edit-secrets`: ограниченная read-only проверка явно переданных рабочих файлов с точным immutable policy release, Gitleaks 8.30.1 и действующими typed waivers. Поддерживаются managed, unmanaged и non-Git проекты; проверяются полные текущие байты и их SHA-256. Результат содержит пути, строки, fingerprint и действие без значения секрета или фрагмента исходников. Проверка работает offline, не изменяет файлы и не запускает историю или полный Gate. Неподдерживаемая кодировка, пропущенное scanner покрытие, повреждение, превышение лимитов и дедлайн дают `unchecked`.

Исправлены fingerprints общего scanner transport для candidate/history/audit: SHA-256 вычисляется из фактического секрета в ограниченной памяти, а не из строки `REDACTED`, подставляемой прежним `--redact=100`. Detector rules и точное сопоставление waiver по check ID, target и fingerprint сохраняются. Необработанные отчёты и журналы не записываются на диск.

Это MAJOR относительно опубликованной v2.6.2: waiver, выданный для SHA256("REDACTED"), больше не подавляет другой фактический секрет. Перед обновлением нужно пересмотреть такие исключения и при необходимости явно переоформить каждый waiver для точного target и настоящего fingerprint. Совместимого псевдонима для ошибочного digest нет. После обновления engine эта коррекция действует и при сохранённом старом policy pin; опубликованные старые wheels не изменяются. Откат требует явного выбора прежнего immutable engine/policy и проверки совместимости сохранённых waiver.

Новый engine поддерживает точные pins v2.4.2/v2.5.0/v2.6.0/v2.6.1/v2.6.2 и новый v3.0.0 после публикации. Ruff schema 1, безопасные исправления и повторное использование результатов не меняются. Запуск native процессов на Windows защищён Job до выполнения дочернего кода. Релиз не устанавливает Codex hooks, не включает secret hook, не заменяет baseline и не обновляет consumer workflow pins автоматически; установку, миграцию legacy-защиты, реальные события и суммарную задержку проверяет host отдельно.
