# Architecture map

Use this map before non-trivial codebase questions, design work, or code changes. Verify relevant claims in code.

## Navigation

- **CLI and orchestration** — `quality_gate/cli.py` parses commands; `quality_gate/contracts.py` validates schema 2 and defines verdicts and timing telemetry; `quality_gate/migration.py` prints read-only schema 1 proposals; `quality_gate/snapshot.py` materializes the read-only Git index candidate and exposes `CandidateSnapshot.index_identity` plus `remove_snapshot` for transferred cleanup; `quality_gate/integrity.py` checks Git hygiene, workflow hygiene, and mechanical documentation health; `quality_gate/lessons.py` validates escaped-defect lessons and release readiness; `quality_gate/runner.py` executes checks and audits against that candidate; `quality_gate/operation.py` owns one monotonic work deadline, stage observations, retained check results, transferred cleanup roots, and the shared bounded cleanup phase; `quality_gate/launcher.py` selects a pinned release and prepares consumer runtimes; `quality_gate/hooks.py` exposes the native Git launch and push protocol; `quality_gate/hook_setup.py` installs managed wrappers safely; `quality_gate/release.py` validates a self-host source and exact release artifact before publication and checks the resolved Windows workspace path against its 180-character limit.
- **Verdict reporting** — `quality_gate/reporting.py` preserves existing outcome lines and appends bounded, redacted operation/check timing and execution disposition; `quality_gate/contracts.py` defines additive `StageTiming` and `OperationTelemetry` alongside verdicts and known/unknown upstream finding-omission metadata.
- **Policy distribution** — `quality_gate/release_contract.py` defines the exact unified-release inventory; `quality_gate/distribution.py` validates release manifests, that inventory, and SHA-256 digests, installs releases through a locked same-volume replacement, quarantines corrupt entries, and retains active/previous selections.
- **Local admission** — `quality_gate/admission.py` owns four user-local OS-locked slots for independent full Gate runs. `runner._run_snapshot` acquires admission before snapshot construction; descendants reuse only a lease confirmed by a live slot lock and matching token. CI skips local admission. See [the local queue contract](local-gate-queue.md) for waiting, Ruff workers, and activation limits.
- **Temporary workspace.** `quality_gate/temp_workspace.py` reclaims an inactive `qg-` directory only when a user-local HMAC key validates its root-level owner record and directory identity, the marker and active-lock identities match, and Gate acquires the run lock. A signed cleanup record binds both control-file identities and permits recovery after partial removal. Keys and cleanup records are published only after complete writes; a separate recovery key preserves an incomplete older key. Deletion checks identity atomically through a Windows file handle or a private POSIX cleanup area selected by key. POSIX retains authenticated areas for journal recovery. A name prefix or marker alone does not authorize deletion. The module preserves foreign files and directories, unrecognized entries, legacy `.quality-gate-edit-*` directories, active runs and the root lock. During an active Gate operation, process-scope and file-lock waits consume the original work deadline, and stale-workspace reclamation runs in a supervised child. Python, child-process, and native-cache staging roots transfer to the operation's one bounded cleanup phase; standalone callers keep synchronous cleanup. Read-only checkouts and candidate snapshots use a private hashed workspace per repository under user-local system temp. Staging beside persistent caches and atomic replacement targets stays beside those targets.
- **Path safety** — `quality_gate/path_safety.py` centralizes symlink and Windows reparse-point predicates shared by edit-input validation, source inventory, native-cache lock paths and temporary-workspace cleanup.
- **Native tool caches** — `quality_gate/native_cache.py` selects persistent Ruff/mypy namespaces under the policy cache using the shared Git directory for linked worktrees, engine version, runtime fingerprint, pinned tool and policy/config identities, platform, Python, effective options, and import roots. Worktrees in one clone can share namespaces; separate clones remain isolated. While holding an OS file-lock lease, the runner copies the current candidate into a stable, read-only source root it owns and derives file timestamps from content so Ruff can reuse matching entries across temporary snapshots. Gate operations cap maintenance-lock and namespace-lease waits by remaining work time, supervise pruning, namespace preparation and source staging against the original deadline, retain the namespace lease until shared cleanup, and revalidate namespace, staging, and owner-marker identities before removal. The parent retains the maintenance lock while maintenance children work, and the namespace lease while preparing that namespace. Standalone callers keep synchronous staging and cleanup. Stale-stage recovery uses the same ownership checks. Unsafe or unavailable staging falls back to the original snapshot with its private cache. The provider evicts only marked inactive namespaces within bounded retention/capacity. `quality_gate/file_lock.py` supplies the shared cross-platform OS-lock mechanism used by cache leases and temporary workspaces. `NativeToolCacheSelection` supplies operation lookup cost, persistent/private storage and bounded fallback observations. Lookup, maintenance and source preparation have separate stages; their workers do not mark Ruff/mypy executed. A selected namespace proves neither a tool-internal hit nor complete-result reuse. Cache selection never skips a tool invocation.
- **Local runtime** — the stable native wrapper reads the staged schema 2 manifest, verifies the declared wheel in the immutable user cache, and launches that exact release without importing mutable repository source; `quality_gate/runtime.py` creates a separate component runtime per repository and fingerprint of policy, component, Python, and dependency inputs.
- **CI integration** — `.github/workflows/quality.yml` is the reusable GitHub workflow boundary; it checks out `job.workflow_repository` at `job.workflow_sha`, bootstraps Python before reading component versions, selects a platform-specific immutable release asset, and uses `quality_gate/ci_release.py` plus `quality_gate/release_contract.py` to verify GitHub release immutability, the GitHub-reported asset digest, the exact unified inventory, every declared release file, and safe extraction paths; `.github/workflows/parity.yml` runs the release-backed Python/web/supplemental fixture on Windows and Linux from dispatch or schedule, uploads machine-readable results, and compares them in a separate job; every external Action is pinned to a full commit SHA, and pull requests pass explicit range refs to the same CLI gate.
- **Project contract** — `quality_gate/contracts.py` is the source of truth for schema 2 repository, Python/web component, supplemental-test, verdict, and waiver models; `quality_gate/policy/biome.json` and `quality_gate/policy/biome.toml` are the pinned web-tool policy and platform inventory; `templates/quality-gate.toml` is the manifest shape and `templates/quality.yml` plus `templates/dependabot.yml` are the consumer CI shapes generated for a project by `$setup-repo`.
- **Learning contract** — `docs/lessons.md` defines the English Markdown lesson format; `quality_gate/lessons.py` validates lessons and provides the audit and release readiness results.
- **Shared publication** — `quality_gate/publication.py` owns PR decisions, version rules, and the bounded lowercase GHCR repository contract; `publication_flow.py` owns source authorization and the publication state machine; `publication_config.py` owns declarative product requirements; `publication_evidence.py` and `publication_artifacts.py` verify attempt-bound Actions provenance and retained envelopes; `publication_github.py` provides bounded GitHub API and registry access; `publication_writer.py` inspects one-image Docker-save-compatible archives and checks their source revision before push. Publisher readback binds image references to the source-configured GHCR package. The prepare, image-writer, and publish reusable workflows call the policy-free `scripts/source_release.py` entry point. Read [the shared interface](publication.md) before changing consumer wiring, evidence, or recovery.
- **Provider activation** — `quality_gate/release_rollout.py` checks publication receipt identities, emits `quality-gate-release-published` after successful publication, and creates or refreshes the provider's no-release activation PR through `.github/workflows/release-rollout.yml`. It advances both policy pins and active assertions and removes only marked temporary waivers. See [the event and recovery contract](release.md#retry-and-provider-handoff).
- **Consumer rollout** — `.github/quality-gate-consumers.json` lists six private consumers and `quality-gate`, routed to its separate provider activation. `quality_gate/consumer_rollout.py` validates the published receipt/tag and static workflow references; `.github/workflows/consumer-release-rollout.yml` isolates tokens, failures, and concurrency per consumer. Shared `release_rollout.py` validates branch inputs before synchronization and refuses an orphan rollout branch.
- **Product release** — `.release/version.toml` is the product-version authority; `.release/notes.md` contains reviewed changes; `.release/publisher.toml` declares product projections and required producers. The provider source manifest stays pinned to the latest published policy through candidate verification, while the consumer template projects the product release; the provider activates its new policy after publication. `scripts/release_build.py` drives the existing platform checks; `scripts/release_adapter.py` owns package construction, installation, and isolated runtime/audit validation; `scripts/release_metadata.py` supplies product metadata. Follow [the local release contract](release.md) when preparing a candidate.

- **Outgoing push secrets** — `quality_gate/hooks.py` validates push updates, selects the pinned scanner and enumerates outgoing commits under one deadline; `quality_gate/secrets.py` scans each commit's parent patches, including roots. Missing or ambiguous history fails closed. Host wrapper activation is a separate deployment boundary; see [the operating guide](agent-reference-operations.md).

- **Runner modules** — `runner_snapshot.py` owns snapshot orchestration; `runner_process.py` owns process and deadline helpers; `runner_domain.py`, `runner_dependencies.py`, `runner_python_checks.py`, `runner_python_tools.py` and `runner_web.py` hold check-specific implementation behind `runner.py`.
- **Read-only product verification** — `quality_gate/product_verification.py` validates product evidence content and transport separately; `scripts/release_build.py` and `scripts/release_adapter.py` produce candidate artifacts. Neither validation alone is a complete CI verdict; see [the verification contract](product-verification.md).

See [architecture flows](architecture-flows.md) for execution and publication paths.
