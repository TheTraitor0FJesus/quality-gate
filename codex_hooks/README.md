# Python Quality для Codex

Это руководство описывает установку и работу Python Quality и Post-edit на Windows. Команды выполняйте из корня локального клона Quality Gate. Нужны Codex, Git и Python 3.11 или новее. Bash и WSL не требуются: matcher shell-событий `^Bash$` принимает имя инструмента Codex Bash, в том числе PowerShell-вызовы. После регистрации оставьте клон доступным по тому же пути.

## Источники и состояние

Исходники и тесты хука находятся в `codex_hooks/` и исключены из публикуемого wheel Quality Gate. Регистрации в `CODEX_HOME/hooks.json` запускают эти файлы непосредственно из checkout. Активный `CODEX_HOME` определяется переменной окружения `CODEX_HOME`; если она не задана, Codex использует `.codex` в профиле пользователя. Настройки `hooks/_shared/python-quality.json` и квитанция `hooks/_shared/python-quality-install.json` принадлежат этому CODEX_HOME, а не репозиторию. Не копируйте исходники Python Quality в каталог резервного копирования хуков: он может продолжать обслуживать другие хуки.

Регистрация хранит пути к исходникам, поэтому перенос checkout при активной установке требует `relocate`. Квитанция хранит SHA-256 файлов управляемого набора. После изменения этих исходников `status` может показать состояние `active`, но не подтверждает актуальность хешей или доставку события Codex. При расхождении источника с установленной квитанцией используйте `rollback`, затем `prepare` и `activate`. Установщики сохраняют посторонние регистрации `hooks.json`; не удаляйте принадлежащие Python Quality группы вручную.

## Временная пауза

Для немедленной паузы уже открытых сессий установите верхнеуровневое поле `paused` в значение `true` в квитанции `CODEX_HOME/hooks/_shared/python-quality-install.json`. Зарегистрированный координатор и Post-edit завершаются без чтения события, сканирования и выдачи отчётов. Сохраните остальные поля квитанции. Пауза не отменяет уже запущенную проверку, для неё используйте штатную отмену фоновых задач.

Дополнительно можно отключить семь обработчиков Python Quality через `/hooks`. Это сохраняет регистрации, но уже открытым процессам может потребоваться перечитать конфигурацию. Поддерживаемая переустановка сохраняет установленную паузу. Для возобновления удалите `paused` или установите `false`, затем включите обработчики Codex. Оба переключателя должны разрешать работу.

## Выпуски и подготовка репозитория

Provider v4.6.0 поддерживает объявленные в манифесте `source_roots` для исходников соседних каталогов. Хук сверяет полный состав каталогов и `.py`/`.pyi` во всех объявленных корнях, включая локальные stubs, а также актуальность `py.typed` и конфигурации. Изменение этих файлов требует новой проверки.

Настройка установки Codex и настройка целевого репозитория отвечают за разные вещи:

- `provider_release` выбирает опубликованный выпуск Quality Gate, который реализует интерфейсы edit-проверок. Он общий для репозиториев, обслуживаемых этой установкой Codex.
- `baseline_release` выбирает закреплённый policy для baseline-механизмов и совместимости интерфейсов.
- `quality.policy_release` в `quality-gate.toml` выбирает policy конкретного репозитория для штатных команд Quality Gate. Обновление provider или локального release cache не меняет это поле.
- `baseline_python` и `baseline_python_version` задают интерпретатор Ruff для этой установки Codex. Они не подменяют версии Python, объявленные компонентами проекта.

Покажите текущие параметры:

```powershell
python -B codex_hooks/_shared/quality_settings.py show
```

Меняйте параметры только поддерживаемой операцией `update`, а не прямой правкой JSON. Например, чтобы выбрать точный опубликованный provider, сохранив остальные поля:

```powershell
$codexRoot = if ($env:CODEX_HOME) { $env:CODEX_HOME } else { Join-Path $env:USERPROFILE '.codex' }
$settingsPath = Join-Path $codexRoot 'hooks/_shared/python-quality.json'
$settingsScript = 'codex_hooks/_shared/quality_settings.py'
$selection = (Get-Content -LiteralPath $settingsPath -Raw | ConvertFrom-Json -AsHashtable).current
$selection.provider_release = Read-Host 'Точный тег опубликованного выпуска, например v4.2.1'
$selection | ConvertTo-Json -Compress -Depth 5 | python -B $settingsScript --file $settingsPath update
python -B $settingsScript show
```

После публикации Quality Gate процедура `post-release-quality-gate` выбирает проверенный тег в `provider_release`, если выпуск поддерживает интерфейсы включённых edit-проверок. Сначала процедура проверяет и устанавливает asset в локальный release cache, затем меняет selector через `quality_settings.py update`, сохраняя остальные параметры. Этот выбор общий для всех репозиториев активной установки Codex и не меняет их `quality.policy_release`. Смена только версии provider не требует повторной регистрации, потому что обработчики читают настройки при запуске и используют исходники из checkout. Если изменились сами файлы `codex_hooks/`, обновите регистрацию по инструкции в разделе «Установка и восстановление Python Quality».

Для каждого целевого репозитория с манифестом объявите Python-компоненты и зависимости, нужные инструментам. Затем из корня этого репозитория выполните `quality-gate sync`, `quality-gate setup` и `quality-gate doctor`. `setup` готовит только компоненты этого репозитория. При изменении зависимостей повторите подготовку и диагностику. Изменения содержимого stubs и полей `stub_roots`/`source_roots` требуют повторной edit-проверки; сами по себе они не меняют fingerprint managed runtime и не требуют нового `setup`. Хук во время правки ничего не скачивает и не устанавливает.

Чтобы временно отключить Types во всех репозиториях этой установки Codex, загрузите текущий объект `current`, удалите только `types` из `$selection.enabled` и передайте объект в `quality_settings.py --file $settingsPath update` тем же способом, что в примере выше. Сохраните остальные поля. Чтобы включить Types снова, прочитайте актуальный объект, выберите совместимый точный `provider_release`, добавьте `types` и снова выполните `update`. Команда `rollback` настроек восстанавливает предыдущее целое состояние, поэтому после смены выпуска проверьте, что она не вернула старый provider. `typecheck = false` действует только на один компонент одного репозитория.

При `types` компонент должен быть доступен для mypy. Укажите в `dependency_inputs` файлы зависимостей с импортируемыми пакетами и файлами описания типов. Если пакет не содержит описаний типов, подготовьте совместимый пакет заглушек. Поле `stub_roots` для локальных `.pyi` допустимо только в выпуске, который реализует этот контракт. Поддержка в исходниках checkout и нижняя граница версии policy сами по себе не доказывают поддержку опубликованным движком. Проверяйте манифест выбранным выпуском через `quality-gate validate` перед подготовкой runtime. Поддерживаемый `typecheck = false` отключает Types только для объявленного компонента; отсутствующее поле означает включённую проверку в policy `v3.1.0` и новее, старые policy могут отвергать поле. `doctor: ready` подтверждает runtime, но не наличие типов для каждого импорта. Причина `unchecked/dependencies` указывает на отсутствующий типовой контекст.

Без манифеста Types использует корневую `.venv` без system-site-packages. Подготовьте в ней зависимости, stubs и версию mypy, которую требует policy. Глобальные системные пакеты не заменяют эту `.venv`.

## Выбор механизмов и порядок проверки

Массив `enabled` в настройках Codex независимо выбирает `ruff`, `secrets`, `integrity` и `types`. Меняйте его через `quality_settings.py update`. Выбор `integrity` сам по себе не включает Ruff или окружение Python. Порядок обработки атрибутированной правки следующий:

1. Координатор сопоставляет `PreToolUse` и `PostToolUse` по matcher-у `^Bash$`, снимкам и изменившимся путям. Для `apply_patch` отдельное событие Post-edit уже передаёт изменённые пути.
2. Выбранный Ruff синхронно применяет безопасные исправления и форматирует изменённые `.py` и `.pyi`. Затем фоновый Ruff повторно проверяет итоговые байты без записи. Оставшиеся ошибки появятся в контексте агента. В Quality Gate `v4.2.1` F401 удаляет неиспользуемый импорт в обычном модуле, сохраняя явные re-export в `__init__.py`.
3. `integrity` синхронно проверяет изменённые файлы на маркеры Git-конфликтов после исправлений Ruff. Она не входит в фоновые проверки.
4. В фоне последовательно запускаются выбранные Ruff, `secrets`, встроенный поиск известных секретов и `types`. `types` анализирует весь затронутый компонент, в том числе неизменённые файлы, которые импортируют изменённые определения. Для удаления файла передаётся факт его отсутствия.

Фоновый встроенный поиск распознаёт известные шаблоны ключей AWS, GitHub и OpenAI, присваивание `AWS_SECRET_ACCESS_KEY` и заголовок закрытого ключа. Он включён в общую фоновую задачу, когда включён `secrets`. Если `secrets` отключён, встроенный поиск выполняется синхронно. В этом случае `CODEX_POST_EDIT_HEAVY_SECURITY=1` дополнительно запускает Semgrep и detect-secrets в общем фоновом процессе. Проверка использует отмену, контроль свежести и доставку результатов текущей сессии. При `Stop` агент может ждать её завершения в пределах бюджета. Ошибка сканера без реальных находок даёт `UNCHECKED`, реальная находка сохраняет статус `failed`. На проверенной Windows-конфигурации глубоко вложенный `TEMP` приводил к ошибке Semgrep; используйте обычный системный TEMP при диагностике этого случая.

Параллельные shell-вызовы сохраняют отдельные снимки и продолжают проверки. Разница между снимками может включать изменения другого агента, поэтому при перекрытии вызовов Ruff проверяет содержимое без автоисправлений. Secrets, Integrity и Types продолжают работать по выбранным настройкам. Совпадение проверяемого файла не доказывает авторство правки. Для последовательного shell-вызова и явных patch-изменений сохраняется обычный порядок с автоисправлениями Ruff. Незавершённый снимок другой сессии сам по себе не запрещает новую проверку.

Чистые проверки и обычное ожидание не порождают сообщения. Ошибки Ruff, выбранного `secrets`, `integrity` и Types поступают в контекст агента, но сами по себе не отменяют уже завершённую shell-команду. Совпадение встроенного поиска секретов блокирует ответ хука. При ошибке атрибуции, отсутствии provider, истечении срока, устаревании или неполном отчёте хук сообщает `unchecked`; это не успех. Результат может поступить на следующем активном событии либо при `Stop`/`SubagentStop`. Уже доставленные одинаковые ошибки Ruff и Secrets повторно не отправляются.

Обработка не запускает полный набор тестов проекта и не доказывает корректность всего репозитория. Secrets и Integrity анализируют только затронутые файлы. Ограничения размера, неподдерживаемые файлы и недоступные зависимости могут оставить проверку неполной.

## Фоновая работа и завершение событий

Python Quality управляет парными `PreToolUse`/`PostToolUse`, `Stop`, `SubagentStop`, `Interrupt` и `SessionEnd` группами. Не удаляйте их по отдельности: пара shell-событий нужна для атрибуции, а события завершения нужны для доставки и очистки. Новая правка отменяет устаревшую работу, сохраняя ещё не проверенные пути и недоставленные результаты. На корень проекта допускается одна актуальная задача; работа, ещё нужная другой сессии, сохраняется при завершении одной сессии.

Shell-захват сохраняет идентификаторы сессии, хода и вызова. `Stop` и `Interrupt` удаляют захваты своего хода только при подтверждённом завершении соответствующих команд. Длинная команда с живой exec-сессией сохраняет захват. `.conflict` удаляется, когда других захватов в группе больше нет. Захваты других ходов и сессий сохраняются; `SubagentStop` не очищает захваты родительского хода.

При следующем `PreToolUse` хук может убрать захват завершённой команды, если подтверждено и завершение её хода. Для отказа запуска действует отдельное условие. Если хост записал `failed`, код `-1` и явное `processId: null`, exec-сессия не началась и хук может убрать её захват уже в текущем ходе. Отсутствующее поле `processId` такого подтверждения не даёт. Это позволяет восстановиться после пропущенного Post, в том числе для старого захвата без идентификатора хода. Подтверждение привязано к точному вызову и сессии. Каталог запуска может отличаться от корня захвата, но для подтверждения самой правки хук по-прежнему проверяет каталог проекта.

Дополнительный адаптер читает только метаданные из локального `thread_history_1.sqlite` под активным `CODEX_HOME`. Это внутренний формат Codex, совместимость с которым нужно проверять после обновления агента. При отсутствии, повреждении или неизвестном формате истории хук сохраняет неподтверждённое состояние и сообщает `unchecked`. Он не создаёт базу и не изменяет её содержимое. Одного возраста файла недостаточно для удаления. `SessionEnd` остаётся штатной очисткой состояния заканчивающейся сессии.

Хост может отклонить команду после Pre-события и вообще не записать её выполнение. Если история подтверждает завершение точного хода, но записи вызова нет, хук переносит его захват в `events/unconfirmed/<ключ-проекта>/`. Хук создаёт новый снимок для следующей команды. Если прежний снимок отличается от нового или их нельзя сопоставить, он один раз сообщает о непроверенных изменениях. При совпадающих снимках предупреждение не требуется. Сохранённый захват не участвует в определении активного пересечения. Этот переход не подтверждает выполнение прежней команды или завершение её процессов. Захват активного или неизвестного хода продолжает защищать атрибуцию.

Текущие исходники движка размещают рабочие каталоги edit-проверок в `temp/qg-*` в корне проверяемого проекта. Общий менеджер удаляет завершённый каталог и при следующих запусках очищает неактивные остатки, сохраняя каталоги работающих проверок по блокировкам. Для недоступного на запись корня действует отдельный fallback в системный temp. Это поведение требует установки выпуска движка с данным изменением; прежние выпуски могут создавать `.quality-gate-edit-*` непосредственно в корне. Хук исключает оба служебных расположения из shell-снимков.

Если Python Quality сам блокирует shell-вызов в `PreToolUse` из-за доставленного сообщения о секрете, он удаляет снимок этого вызова: соответствующего `PostToolUse` не будет. Информационное сообщение, которое разрешает выполнение команды, сохраняет снимок до парного события.

Настройка `budget_seconds` по умолчанию равна 10 секундам и допускает значения от 0.1 до 10 секунд. Это срок синхронных исправлений Ruff, Integrity и постановки фоновой работы. Общая фоновая задача имеет до 30 секунд работы и до 3 секунд очистки процессов. Ожидание `Stop`/`SubagentStop` также учитывает доставку и свежесть результата; регистрация задаёт для него 45 секунд. `SessionEnd` отменяет работу заканчивающейся сессии. `Interrupt` отменяет её фоновую работу в пределах 3 секунд и не блокирует прерывание или перезапускает ход. На Windows блокировка файла состояния повторяется не более 0.5 секунды и не дольше срока события.

Ожидайте сообщение о проблеме или неполной проверке. Отсутствие сообщения означает лишь, что хук не сообщил результат в этом событии. Регистрация и успешный прямой запуск обработчика не доказывают доставку события Codex. После установки перезапустите Codex, проверьте определения командой `/hooks`, подтвердите доверие, если Codex его запросит, затем проверьте реальное событие редактирования и доставленный результат.

## Установка и восстановление Python Quality

Запустите команды из корня checkout:

```powershell
python -B codex_hooks/python_quality/install_python_quality.py status
python -B codex_hooks/python_quality/install_python_quality.py prepare
python -B codex_hooks/python_quality/install_python_quality.py activate
python -B codex_hooks/python_quality/install_python_quality.py rollback
```

`status` показывает состояние квитанции, а не проверяет актуальность исходников и реальную доставку событий. `prepare` создаёт или сверяет управляемые регистрации и локальные файлы состояния. `activate` проверяет именно выбранные механизмы и включает установку. Если выбран `types`, передайте `--typing-probe-root <абсолютный-путь>` к заранее подготовленному проекту с корректным `probe.py`; activation probe действительно запускает проверку и ничего не устанавливает. `rollback` отменяет собственную фоновую работу, очищает список включённых механизмов и удаляет шесть групп Python Quality, сохраняя чужие регистрации.

Изменения установщика в `hooks.json` выполняются под общей блокировкой. По умолчанию ожидание блокировки ограничено 10 секундами; значение можно изменить полем `install_lock_wait_seconds` объекта `current` в `hooks/_shared/python-quality.json`. Допустимый диапазон — от 0.1 до 120 секунд. Если блокировка не освободится вовремя, установщик завершится до записи `hooks.json`.

Если изменились исходники после установки, последовательно выполните `rollback`, `prepare`, восстановите нужный список механизмов поддерживаемым `update`, затем `activate`. При переносе активного checkout выполните из нового корня:

```powershell
python -B codex_hooks/python_quality/install_python_quality.py relocate
```

`relocate` обновляет пути в принадлежащих хуку регистрациях и квитанции. Она сохраняет выбранные механизмы и посторонние регистрации. Если `status` сообщает `active`, но событие даёт `Restore hook prerequisites`, проверьте соответствие исходников квитанции и повторите подготовку установки после отката.

## Post-edit для apply_patch

Регистрация Post-edit независима от шести групп Python Quality. Её установщик добавляет только обработчик `PostToolUse` с matcher-ом `apply_patch`:

```powershell
python -B codex_hooks/python_quality/install_post_edit_hook.py status
python -B codex_hooks/python_quality/install_post_edit_hook.py install
python -B codex_hooks/python_quality/install_post_edit_hook.py uninstall
```

При активном Python Quality обработчик передаёт изменённые пути общему координатору. Когда Python Quality не активен, применяется запасной обработчик: `ruff check --fix`, `ruff format` для изменённых `.py` и встроенный поиск секретов по поддерживаемым файлам. При `CODEX_POST_EDIT_HEAVY_SECURITY=1` он дополнительно запускает Semgrep и detect-secrets. Fallback не запускает Integrity или Types. Ошибки Ruff и безопасности в этом режиме возвращаются блокирующим ответом после правки; правка уже произошла и автоматически не отменяется. Post-edit не запускает тесты проекта. `uninstall` удаляет только свою регистрацию PostToolUse.

## Типы, лимиты и самостоятельный запуск

Types использует mypy выбранной policy и её правила импортов. Результат не проверяет динамические импорты и не доказывает корректность всего репозитория. Поддерживаются не более 10 входных файлов, 128 KiB на файл и 1 MiB на группу входа; область анализа ограничена 1024 исходниками и 16 MiB. Снимок окружения ограничен 20 000 записями и 512 MiB. Отчёт содержит не более 200 диагностик и 256 KiB. Превышение предела даёт неполный результат. Вывод не включает исходные фрагменты и свободные сообщения mypy.

Для проекта без манифеста область Types исключает скрытые имена, `__pycache__`, `site-packages`, `node_modules`, `build`, `dist` и `temp`. В управляемом компоненте используется discovery выбранного mypy; окружение проверяется отдельно. Каждый запуск использует отдельный временный кэш mypy, постоянного инкрементального кэша нет.

Самостоятельный вход `codex_hooks/python_types/check.py` принимает JSON со `schema: 1`, абсолютным `root` и массивом `files`. Каждый элемент содержит относительный `path` и SHA-256 текущих байтов; для удалённого пути передайте `sha256: null`. `--background --session-id <id>` ставит задачу в очередь. Без `--background` синхронная проверка использует `budget_seconds` от 0.1 до 10 секунд. Для ожидания фонового результата или отмены используйте тот же session ID:

```powershell
python -B codex_hooks/python_types/check.py --drain --session-id <id>
python -B codex_hooks/python_types/check.py --cancel --session-id <id>
```

При собственных `--settings` и `--state-dir` передавайте те же пути при постановке, ожидании и отмене; каталог состояния должен быть вне проекта. `pending` подтверждает только постановку. После `drained` прочитайте отчёты и код завершения. Отменённая, устаревшая, недоставленная или завершившаяся `unchecked` проверка не считается успехом.

Подробный wire-контракт edit-проверок приведён в [edit-types](../docs/edit-types.md), а интерфейсные требования при изменении Quality Gate — в [release guide](../docs/release.md#working-tree-interface-verification).

### Действия по диагностике

Поля безопасной диагностики, сохранение причины неудачного Pre и порядок восстановления описаны в [диагностическом контракте](DIAGNOSTICS.md). Неизвестные сведения обозначаются явно. Идентификатор фонового задания отделён от идентификатора исходного вызова инструмента.

При реальной находке `ACTION REQUIRED` требует исправить её в рамках задачи. Следующую правку хук проверит автоматически; инструкция не требует отдельного ручного запуска проверки. Для `UNCHECKED` инструкция требует немедленно доложить пользователю о неполной проверке, указать проверку, диагностику, репозиторий, затронутые пути и доступный путь к отчёту без исходников и секретов. Недоступные сведения нужно обозначить явно. Если пользователь уже разрешил диагностику или исправление этой неполной проверки, агент продолжает работу в согласованных пределах и сообщает о ходе исправления. Повторное сообщение о той же нерешённой проблеме не требует нового разрешения. В остальных случаях агент приостанавливает задачу и ждёт указаний пользователя перед восстановлением prerequisites или продолжением работы. Успешные, неприменимые и ещё выполняющиеся проверки остаются без диагностического сообщения. Подтверждение доставки не доказывает исправления; текст инструкции не гарантирует подчинения модели.
